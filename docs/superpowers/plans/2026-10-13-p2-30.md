# P2-30 Output-controller isolation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Configuration changes and a failed output must not dispose a shared supervisor, race a disposed gate, or terminate the routing host.

**Architecture:** Keep the supervisor alive across configuration generations. A registry supplies one serialized controller per physical output; the controller owns its reservation, current session/purpose and operation lifetime. Coordinator policies submit start/stop intents through the supervisor; process mutation is executed inside the output controller. An uncertain operation retains ownership and alarms rather than permitting a replacement writer.

**Tech Stack:** .NET 8, C#, xUnit, fake child processes, injected supervision clock, existing SQLite/telemetry.

**Spec:** Owner-approved Phase 2 plan, section P2-30 (private source document); follow-ups require one test-first PR, owner-only merge, production read-only, R18 left for Phase G.

## Global Constraints

- No production connection or hardware operation for this task. No GPU/runtime/driver changes.
- Preserve the original 136 tests and current healthy-media policies. Tests must assert the new correct recovery contract, not preserve whole-host termination.
- Build from merged main; a separate guarded bench candidate remains immutable.
- Existing children retain their process settings and shutdown budget; edits apply to future starts only.
- No new operator knobs. Operational deadlines are bounded constants plus the existing graceful-stop budget.
- No disposal of gates with outstanding users; no unbounded native-process cleanup wait.
- One fresh whole-PR review; one test-first Important/Critical correction pass; no merge by agent.

## Review Focus

1. Different source IDs targeting the same physical port: one writer, including standby/live collision.
2. Settings changed while a child or its stop is active: old owner untouched, next start uses new generation.
3. Native/process work that ignores cancellation: caller bounded, ownership retained, other outputs usable.
4. Disposal racing queued starts/exits/stops: starts refused once shutdown begins; no disposed-gate exception or orphan.
5. Watchdog storage failure or controller uncertainty: visible alarm, no unrelated child termination or host FailFast.
