# P2-10 — bounded standby lifecycle (software qualification)

## Root cause and test-first evidence

An OS process launch was immediately reported as running standby, before any
frame. Both idle standby reconciliation and route-fallback monitoring could
replace an early-exiting child on every pass. Commit 79eb12c first reproduces
optimistic Running and 60 starts in one simulated minute in both paths. The
correct expectation is Starting, then only three early attempts before a circuit.

## Changes

- One in-memory retry budget per output, shared by idle and route fallback:
  1/2/5/10/20/30 seconds plus non-negative jitter.
- Three failures within 60 seconds open a sticky circuit. Emit one alarm with
  redacted recent stderr; retry no sooner than five minutes. Keep the failed
  status visible during half-open media qualification.
- Process launch alone is Starting. Missing first-frame progress reaches the
  configured startup deadline and retires that exact owned process. Route
  fallback likewise remains Reconnecting until the first generated frame.
- Intentional stops do not count as startup failures. Reset debt only after
  60 seconds of continuous observed progress, using the P2-12 stability policy.
- All replacement work remains under the output gate and existing ownership
  checks. No changes to input watchdog thresholds or Windows containment.

## Independent review and fix pass

The fresh reviewer rejected candidate 46066ef: one Critical ownership race and
three Important policy/eligibility defects. Commits 25bdd25, 1b9f017 and e6884f4
record the six correctly failing assertions before their fixes:

- Stop followed by a queued stale fallback could leave both source fallback and
  idle standby alive on one output. The periodic path now takes route then port
  gates, rereads current intent, and rejects route changes during the port wait.
- Monitoring and reconciliation reread the same progress sample, continually
  erasing the stable minute. Identical fresh samples are now idempotent; stale,
  unhealthy, regressed or newly non-advancing evidence still resets the window.
- A queued fallback could launch after simulation/validation/filter eligibility
  changed. Those checks and device/preset/config resolution now occur after the
  port gate, before launch.
- Interleaved retained failures could charge the same session twice. Bounded
  session accounting now covers the supervisor's retained-exit capacity. Launch
  exceptions do not evict real failed-session identities. Boundary tests check
  the capacity and that rereading stale progress never qualifies recovery.

Fix pass: six red assertions to green; full main 246/246. The reviewer verified
the original candidate independently; the implementer verified the fix pass.
